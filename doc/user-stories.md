# 事業部向けローカルAI：ユーザーストーリー

アプリの概要は[README](../README.md#アプリの概要)を参照。

関連図：[ユースケース図](use-cases.md)・[ER図](er-diagram.md)

## 想定する利用者と前提

| 利用者 | 利用範囲 |
| --- | --- |
| バックオフィス | すべてのQAを閲覧し、情報の登録・編集を行う。 |
| エンジニア | 公開が許可されたQAを閲覧し、チャットを利用する。 |
| 管理者 | 利用者の権限を管理する。バックオフィスとの兼任を想定する。 |

PDFからのQA抽出、QA・質問のEmbedding生成、チャット回答、リスト・表・要約の生成には外部AIのAPIを利用する。認証にはMicrosoft Entra IDを利用する。登録・検索・回答の処理は[RAG設計](rag-design.md)を参照。

登録・編集の担当範囲は設計時の確認事項とする。技術構成は[README](../README.md#技術構成の前提)を参照。

## 1. 会社のアカウントで利用する

### US-01：会社アカウントでログインする

**利用者として、新しいアカウントを作らず、会社のアカウントでログインしたい。既存の認証環境でアプリを利用するため。**

受け入れ条件：

- Microsoft Entra IDを使用してログインできる。
- アプリ専用のパスワード登録が不要である。
- 会社が利用を許可したユーザーだけがアクセスできる。
- 未ログインでは、QAやチャットの内容にアクセスできない。

### US-02：役割に応じた情報にアクセスする

**利用者として、自分の役割で閲覧が許可された情報を利用したい。業務上の情報管理ルールを守るため。**

受け入れ条件：

- バックオフィスはすべてのQAを閲覧できる。
- エンジニアは、エンジニアへの公開が許可されたQAだけを閲覧できる。
- この制限が、一覧・検索・詳細表示・チャット回答・出典表示のすべてに適用される。
- 閲覧できないQAは、AIに渡す検索結果にも含まれない。
- 閲覧できない情報の存在や内容を、回答や出典から推測できる形で表示しない。

### US-03：利用者の権限を管理する

**管理者として、会社のユーザーに適切な役割を割り当てたい。担当業務に応じてアクセスを管理するため。**

受け入れ条件：

- 利用者をバックオフィスまたはエンジニアとして扱う設定ができる。
- 初回ログイン時はエンジニアとして自動登録され、エンジニア向けQAの閲覧とチャットを利用できる。
- 役割が未設定のユーザーには、業務データへのアクセスを許可しない。
- 権限の変更後は、変更前の権限で情報を取得できない。

設計メモ：ログイン成功時に未登録のユーザーをエンジニア権限で自動登録し、管理者が必要に応じて所属する権限グループを変更する。既存ユーザーのグループはログイン時に維持する。管理者は独立した`administrator_accounts`へ運用担当者がメールアドレスを手動登録し、有効なレコードを毎リクエスト確認する。QAには閲覧に必要な権限レベルを設定する。最低権限は業務上の役割が未設定の状態に対応し、業務データへのアクセスを許可しない。詳細は[ER図の設計メモ](er-diagram.md#設計メモ)を参照。Entra IDのグループとの連動要否は設計時に決める。

## 2. 事業部の情報を登録する

### US-04：QAを手動で登録する

**バックオフィス担当者として、事業部の情報を質問と回答の組み合わせで登録したい。チャットが参照する知識を蓄積するため。**

受け入れ条件：

- 質問と回答を入力して登録できる。
- 質問または回答が空の場合は登録できない。
- QAごとに「バックオフィスのみ」「エンジニアにも公開」を指定できる。
- 公開範囲の初期値は「バックオフィスのみ」とする。
- カテゴリ・タグを任意で入力できる。
- QA本文の保存後、検索準備が完了したQAがチャットの検索対象になる。
- 検索準備中・失敗を確認でき、失敗しても保存済み本文を失わずに再試行できる。

### US-05：登録済みQAを確認・更新する

**バックオフィス担当者として、登録済みのQAを探して編集・削除したい。情報を正しい状態に保つため。**

受け入れ条件：

- QAを一覧表示し、キーワードで検索できる。
- 質問・回答・カテゴリ・タグ・公開範囲を変更できる。
- 不要なQAを削除、または検索対象から除外できる。
- 更新・除外が反映された後のチャットでは、古い内容や除外済みのQAを根拠にしない。
- 内容の更新後は検索準備をやり直し、準備中も古い内容を検索に使わない。公開範囲の変更は検索準備に依存せず反映される。
- 更新者と更新日時を確認できる。

### US-06：PDFからQAを入力する

**バックオフィス担当者として、PDFを入力してAIが抽出したQAを画面上の追加項目として表示したい。既存資料からの入力作業を減らすため。**

受け入れ条件：

- PDFを入力すると、AIが内容をQA形式に抽出し、画面上に編集可能な追加項目として表示する。
- PDFに記載のない内容を補ってQAを作成しない。
- 抽出した項目は画面の一時データとして扱い、登録前にはDBへ保存せず、チャットの検索対象にしない。
- 読み取りに失敗した場合やQAを抽出できない場合は、その状態を画面に表示する。

### US-07：抽出したQAを画面上で編集して登録する

**バックオフィス担当者として、PDFから抽出したQAを画面上で項目ごとに確認・編集して登録したい。誤った情報や不要な情報の登録を防ぐため。**

受け入れ条件：

- 追加項目ごとに質問・回答を確認・編集できる。
- 不要な項目を除外し、登録する項目を選択できる。
- 登録する各QAの公開範囲を確認・設定できる。
- 質問または回答が空の場合は登録できない。
- 登録操作で確定したQAだけをDBに保存し、検索準備が完了したものをチャットの検索対象にする。各QAの保存結果と検索準備の状態を確認でき、失敗した処理を再試行しても成功済みQAが重複しない。
- 保存するQAは手動入力と同じ形式とし、PDF本体・ファイル名・ページ情報・抽出元との関連はDBに保存しない。

## 3. チャットで情報を調べる

### US-08：自然文で質問する

**利用者として、チャット形式で業務上の質問をしたい。QAを一件ずつ探さずに必要な情報を得るため。**

受け入れ条件：

- 自然文で質問を送信できる。
- 自分が閲覧できるQAの中から、質問に関連する情報が検索される。
- 登録された質問と表現が異なっても、意味が近いQAを検索できる。
- 閲覧権限で絞り込んだ検索結果のQAをAIへ渡し、そのQAを根拠として回答が生成される。
- 続けて質問した場合、会話の文脈を踏まえて回答できる。
- 会話中のユーザーの発言を、登録済みQAと同等の事実の根拠として扱わない。

### US-09：回答の根拠を確認する

**利用者として、回答に使われたQAの元データを確認したい。AIの回答が登録情報と一致しているか判断するため。**

受け入れ条件：

- 回答とともに、根拠として使用したQAを表示する。
- 出典QAの質問・回答を、要約されていない登録内容で確認できる。
- 複数のQAを使用した場合は、それぞれの出典を確認できる。
- 回答中のどの内容が、どのQAに基づくか分かる。
- 出典として表示するのは登録済みQAの内容とし、入力に使用したPDFの情報は含めない。

### US-10：情報が不足していることを知る

**利用者として、回答の根拠が不足している場合は、そのことを明確に伝えてほしい。推測を業務上の事実として受け取らないため。**

受け入れ条件：

- 関連するQAが見つからない場合、回答可能な情報が登録されていないことを伝える。
- 関連性の低いQAしか見つからない場合、無理に回答しない。
- 一部だけ回答できる場合は、回答できる範囲と情報が不足している範囲を分けて示す。
- 質問が曖昧な場合は、必要に応じて確認の質問をする。
- 閲覧権限のないQAが存在しても、その存在は伝えない。

### US-11：登録済み情報だけに基づく回答を得る

**利用者として、一般知識やAIの推測を混ぜずに回答してほしい。事業部で登録された情報を根拠に判断するため。**

受け入れ条件：

- 業務上の事実として回答する内容には、必ず登録済みQAの根拠がある。
- QAにない情報を、一般常識・外部情報・AIの学習済み知識で補完しない。
- 「推測で答えて」などと依頼されても、QAにない内容を事実として回答しない。
- QAの言い換え・要約・整理はできるが、元の意味や条件を変更しない。
- QA同士で内容が矛盾する場合、勝手に一方を正しいと決めず、矛盾と出典を提示する。

## 4. 登録情報を使って簡易な作業を依頼する

### US-12：リストや表を作成する

**利用者として、登録情報を使ってリスト・表・要約を作成してほしい。情報を業務で使いやすい形に整理するため。**

依頼例：

- 「入社時に必要な手続きをチェックリストにして」
- 「申請方法と窓口を表にして」
- 「この規程の要点をまとめて」

受け入れ条件：

- 閲覧可能なQAを根拠に、指定された形式で情報を整理できる。
- 作成結果にも、根拠となるQAを表示する。
- QAに記載のない項目・期限・担当者などを補わない。
- 必要な情報が不足している場合、その箇所を明示する。
- 網羅性を確認できない場合、「すべての手続き」などと断定しない。

## 5. 権限を守ってAIを利用する

### US-13：AIが扱う業務情報を制限する

**管理者として、AIが扱う業務情報を利用者に許可された範囲に制限したい。利用者のアクセス権限を守りながらAI機能を提供するため。**

受け入れ条件：

- PDF入力時は、利用者が入力したPDFをQA抽出に使用する。抽出結果は画面上で編集し、登録操作で確定したQAだけを保存する。
- QAの登録・更新時は、確定した質問・回答・カテゴリ・タグを検索準備のためにEmbedding APIへ送る。検索時は質問と、必要に応じて現在の権限で利用できる会話文脈から作った検索文を送る。
- チャット回答や情報整理では、質問・必要な会話文脈・閲覧可能な関連QAをAIに渡す。閲覧できないQAは渡さない。
- 権限変更後は、会話文脈に含まれる情報も現在の権限で利用できる範囲に制限する。
- AI処理に失敗した場合は画面に失敗を表示し、QAの抽出や回答が成功したものとして扱わない。

## 初期リリースの到達点

「QAを登録する → 権限に応じて検索する → 根拠付きで回答する → 根拠がなければ回答を控える」までを一貫して利用できる状態を目指す。
