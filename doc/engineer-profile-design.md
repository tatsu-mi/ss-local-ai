# エンジニア情報のDB・RAG設計

## 目的と適用範囲

エンジニアの基本情報・スキル・業務経験を登録し、チャットから候補者検索と個人の経歴に関する質問に答える。既存の業務QAとは検索先を分け、認証・権限確認・回答の根拠表示は共通化する。本書は追加機能の設計であり、現在のアプリに実装済みであることは意味しない。

利用例：

- 「Python経験が3年以上で、AWSの設計経験がある人は？」
- 「金融系案件でリーダーを担当した人は？」
- 「この案件と田中さんの経験が合う根拠を教えて」

氏名・所属・稼働状況・スキル名・経験年数など、厳密な条件はDBで絞り込む。担当内容・成果・業界などの自由記述は業務経験単位でEmbeddingを作り、意味検索する。両方が指定された質問では、構造化条件を満たすエンジニアの経験だけを意味検索する。近い文章が見つかっただけで、年数や資格などの条件を満たしたと判断しない。

## データモデル

| テーブル | 主な項目 | 用途 |
| --- | --- | --- |
| `engineer_profile` | ID、表示名、所属、稼働状況、概要、閲覧レベル、状態、更新日時・更新者 | 検索対象者の基本情報。ログイン用`app_user`とは別管理とし、本人が利用者でもある場合だけ任意の`app_user_id`で対応づける |
| `engineer_skill` | ID、エンジニアID、正規化したスキル名、経験月数、根拠メモ、更新日時 | スキルごとの厳密な絞り込み。経験月数が不明ならNULLにし、0か月と区別する |
| `engineer_experience` | ID、エンジニアID、案件名または案件識別子、業界、期間、役割、担当内容、成果、出典参照、版、状態、Embedding、生成状態・設定版 | 案件単位の経歴と意味検索。機密情報は登録前に除外する |

スキル表記は入力時に同義語辞書で正規化し、原表記も保持する。期間から経験月数を計算する場合は重複期間を二重計上せず、計算方法と基準日を明示する。自己申告の年数と計算値を混同しない。出典参照には、元のスキルシートや登録記録の識別子・該当箇所を記録できるようにする。ファイル本体の保存先と保持期間は実装時に決める。

プロフィール・スキル・業務経験はエンジニアIDで結び、更新・除外・削除を連動させる。閲覧権限はプロフィール単位を基本とし、経験にさらに厳しい制限が必要な場合は経験単位の要求レベルも持たせ、双方を満たす場合だけ表示する。非公開や削除扱いのプロフィール・経験は検索対象にしない。

## 登録・更新

手入力、CSV、スキルシートなどを入力元とする。PDFやWordから抽出する場合、抽出結果を画面で確認・修正してから登録する。元資料にないスキル・年数・役割をAIが補わない。重複候補を示し、既存エンジニアの更新か新規登録かを担当者が確定する。

基本情報とスキルはDBへ保存する。業務経験の意味検索対象フィールドを変更したときは版番号を増やし、古いEmbeddingを同じトランザクションで無効化する。現在の版・設定に対するEmbedding生成が成功した経験だけを意味検索に出す。生成失敗時も本文を保持し、状態表示と再試行を用意する。プロフィールの閲覧権限・状態変更は再Embeddingを待たずに反映する。登録者・更新者・日時を記録する。

## チャットの検索先選択

チャット入力欄に検索先の選択肢「QA」「エンジニア情報」を置き、既定値を「QA」とする。「QA」ではQAだけを、「エンジニア情報」ではエンジニアの基本情報・スキル・業務経験だけを検索し、選択していない情報源をGeminiへ渡さない。質問文から検索先を自動判定しない。選択中の情報源では答えられない場合も別の情報源へ自動で切り替えず、必要なら切り替えを案内する。エンジニア情報を閲覧できない利用者には選択肢を表示せず、サーバーでも指定を拒否する。

検索先は会話単位で固定し、会話の画面と履歴に表示する。選択を変えたら新しい会話を開始する。追質問の文脈には同じ会話・同じ検索先で、現在も閲覧できる内容だけを使う。サーバーは会話に保存された検索先とリクエストの指定が一致することを確認する。既存の会話は移行時に「QA」として扱う。

## エンジニア情報を選択したときの検索と回答

```mermaid
flowchart LR
    Q["エンジニア情報を選択して質問"] --> A["認証・会話の検索先・現在の権限を確認"]
    A --> I["質問からエンジニア検索の条件を解析"]
    I --> D["DBでプロフィール・スキルを絞り込み"]
    D --> V["自由記述があれば候補者の経験を意味検索"]
    V --> G["確認済みの事実と経験本文をGeminiへ渡す"]
    G --> C["出典・版・権限を再確認して回答"]
```

1. 保存済みの会話の検索先が「エンジニア情報」であることを確認する。人名や案件条件が曖昧なら確認する。LLMが抽出した条件はサーバーで許可済みの列・比較演算・値に検証し、任意SQLは実行しない。
2. DBで現在閲覧できる`active`なプロフィールを絞り込む。スキル名、経験月数、所属、稼働状況などの確定条件はSQLで判定する。「情報なし」を条件不一致と区別する。
3. 自由記述の条件があれば、絞り込んだ候補者に属し、現在閲覧できる`ready`な業務経験の中で類似検索する。固有名詞やスキル名の取りこぼしは実データで評価し、必要ならキーワード検索を併用する。構造化条件だけの質問はベクトル検索を必須にしない。
4. 回答生成には、DBで確認した値と取得した経験本文・ID・版だけを渡す。候補者の氏名と各条件を満たした根拠を示し、根拠に使った登録内容をエンジニアIDに対応づける。回答直前にプロフィール・スキル・経験の版、状態、権限を再確認し、変更があれば結果を破棄して再検索する。
5. 該当者なし、検索上限で網羅性を確認できない、記録が足りない場合を区別する。適合度を数値化したり、「情報なし」を「経験なし」と言い換えたりしない。人数・全件一覧が必要な場合はDB側で件数とページングを扱い、少数のRAG候補だけで全件と断定しない。

## 出典表示とエンジニア詳細ページ

「エンジニア情報」の回答では、根拠として使用したエンジニアを出典一覧に1人1件で表示する。各項目は表示名と回答に関係するスキル・業務経験の短い要約を示し、`/engineers/{engineer_id}`のエンジニア詳細ページへリンクする。回答内の出典マーカーもエンジニア単位に対応させる。複数のスキルや案件を使って同じ人を説明しても、出典一覧には重複表示しない。

詳細ページでは、閲覧可能な基本情報・スキル・業務経験を元の登録内容で確認できる。可能なら回答に使ったスキルや案件の箇所へ移動できるようにする。ページを開くたびにサーバーで現在の閲覧権限とプロフィール・各経験の状態を確認し、非公開・削除済みの項目は表示しない。URLを知っているだけでは閲覧できない。

画面上の出典はエンジニア単位だが、回答の検証と履歴のため、内部には根拠に使った`プロフィールID＋版`、`スキルID＋版`、`業務経験ID＋版`と出典マーカーの対応を保存する。チャット履歴に依存した全レコードのID・版を記録し、後で権限喪失・更新・除外が起きた回答は本文も再表示しない。QA会話には既存のQA出典だけを使う。

## 権限と運用

初期案はエンジニア情報の閲覧と管理をバックオフィス権限に限定する。管理操作は閲覧レベルと別の`can_manage_engineer_profiles`で判定する。エンジニア本人や他部門への公開が必要になった場合は、プロフィール・経験の公開範囲と本人閲覧の要件を確定してから追加する。検索候補の絞り込み、詳細API、出典、エクスポート、履歴、Geminiへ送る内容に同じ権限を適用する。

外部Gemini APIへは、Embedding対象の業務経験本文と、回答に必要なプロフィール・スキル・経験だけを送る。個人情報を含むため、収集項目、閲覧者、元資料の保管、更新頻度、退職者の扱いを運用開始前に決める。

## 実装と検証の境界

既存のQA用`qa`テーブルや検索RPCをエンジニア情報の保存先として流用しない。新テーブル、会話の検索先を固定するマイグレーション、管理画面、検索API、エンジニア詳細ページ、出典型、権限テストを追加する実装は別作業とする。評価では、既定のQA検索、明示選択したエンジニア検索、検索先変更時の新規会話、検索先の偽装や権限喪失、別の情報源への自動切替が起きないことに加え、年数の境界、同義語、複数スキルのAND条件、業界・役割の言い換え、重複案件、情報欠落、更新中の旧Embedding、回答と出典エンジニアの一致、詳細ページの権限を確認する。
